## 1. 错误类型统计

### 1.1 网络错误（os error 49 - 端口耗尽）

**总数**：17,602 次

**按交易所分布**：
- Bybit：11,778 次（66.9%）
- OKX：11,732 次（66.6%）
- Binance：11,694 次（66.4%）

**问题分析**：
- `os error 49` 表示本地端口耗尽（`Can't assign requested address`）
- 这是**本地网络资源限制**，不是交易所 API 限流
- 可能原因：
  1. 并发连接数过高，超过系统端口池限制
  2. 代理服务器（127.0.0.1:7890）连接数达到上限
  3. 连接没有及时释放，导致端口泄漏

**影响**：
- ⚠️ **数据丢失**：这些请求直接失败，不会重试（在重构前）
- ⚠️ **严重影响收集效率**：约 17,602 次请求失败

### 1.2 429 限流错误

**总数**：34,297 次

**按交易所分布**：
- Gate.io：16,179 次（47.2%）
- Binance：10,394 次（30.3%）
- OKX：9,230 次（26.9%）
- Bybit：545 次（1.6%）

**问题分析**：
- Gate.io 的限流最严格（占近一半的 429 错误）
- Binance 也有大量限流（可能是 IP 被封禁的副作用）
- OKX 的限流也较为严格

**重试机制效果**：
- ✅ **重试成功**：34 次（虽然数量较少，但说明重试机制在工作）
- ⚠️ **重试成功率较低**：大部分 429 错误在重试后仍然失败

## 3. 核心问题分析

### 3.1 本地端口耗尽（os error 49）⭐⭐⭐

**严重性**：**最高**

**根本原因**：
1. **并发连接数过高**：
   - 虽然使用了 Semaphore 限制并发（每个交易所 2-10 个并发）
   - 但 5 个交易所 × 每个交易所多个 symbol × 每个 symbol 3 个请求（现货、期货、资金费率）
   - 总并发连接数仍然很高

2. **代理服务器瓶颈**：
   - 所有请求都通过 `127.0.0.1:7890` 代理
   - 代理服务器的连接池可能已满
   - 代理可能也有速率限制

3. **连接未及时释放**：
   - HTTP 客户端可能没有正确复用连接
   - TIME_WAIT 状态的连接占用端口

**解决方案**：

1. **进一步降低并发数**：
   ```rust
   // 当前配置
   Okx: 2 个并发
   Binance: 10 个并发
   Bybit: 8 个并发
   
   // 建议降低到
   Okx: 1 个并发
   Binance: 5 个并发
   Bybit: 3 个并发
   Gate.io: 2 个并发
   Bitget: 3 个并发
   ```

2. **增加批次间延迟**：
   ```rust
   // 当前：3000ms (3秒)
   // 建议：增加到 5000ms (5秒) 或更长
   ```

3. **优化 HTTP 客户端**：
   - 启用连接池复用
   - 设置合理的连接超时
   - 使用 keep-alive

4. **减少每个 symbol 的请求数**：
   - 考虑串行请求而不是并行（现货、期货、资金费率）

### 3.2 Gate.io 限流严重 ⭐⭐

**严重性**：**高**

**数据**：
- Gate.io 占所有 429 错误的 47.2%
- 可能的原因是 Gate.io 的限流比其他交易所更严格

**解决方案**：
- 进一步降低 Gate.io 的并发数和请求速率
- 增加 Gate.io 重试的退避时间
- 考虑为 Gate.io 单独设置更保守的策略

### 3.3 数据丢失率高 ⭐⭐⭐

**严重性**：**最高**

**数据**：
- **12,058 个 Symbol 完全没有数据**
- 大量 Symbol 只有 1 个交易所的数据

**影响**：
- 套利分析无法进行（需要至少 2 个交易所的数据）
- 数据完整性严重受损

**解决方案**：
1. **立即解决端口耗尽问题**（见 3.1）
2. **实施数据补偿机制**：
   - 记录失败的 Symbol
   - 在下次检查时优先重试这些 Symbol
3. **增加监控告警**：
   - 当数据完整性低于阈值时告警
   - 监控每个交易所的成功率
