# Crypto Hunter 架构设计文档

## 1. 系统概述

Crypto Hunter 是一个高性能的数字货币交易所套利发现平台，使用 Rust 语言实现。系统设计遵循以下原则：

- **高性能**: 利用 Rust 的零成本抽象和异步并发能力
- **可扩展性**: 模块化设计，易于添加新交易所和功能
- **实时性**: 低延迟数据收集和处理
- **可维护性**: 清晰的架构层次和代码组织

### 2.2 核心模块

#### 2.2.1 交易所适配器层 (`exchange/`)

**设计模式**: Strategy Pattern + Trait Object

**职责**:
- 封装不同交易所的API调用
- 提供统一的接口 `ExchangeAdapter` trait
- 实现具体的交易所适配器

**关键组件**:
- `ExchangeAdapter`: 定义统一接口
- `ExchangeManager`: 管理所有交易所适配器
- `BinanceAdapter`, `OkxAdapter`, `BybitAdapter`, `GateioAdapter`: 具体实现

**扩展性**:
- 新增交易所只需实现 `ExchangeAdapter` trait
- 支持 DEX 扩展（未来）

**示例**:
```rust
#[async_trait]
pub trait ExchangeAdapter: Send + Sync {
    fn exchange_type(&self) -> ExchangeType;
    async fn fetch_spot_pairs(&self) -> Result<Vec<TradingPair>>;
    async fn fetch_futures_pairs(&self) -> Result<Vec<TradingPair>>;
    async fn fetch_spot_price(&self, symbol: &str) -> Result<PriceData>;
    async fn fetch_futures_price(&self, symbol: &str) -> Result<PriceData>;
    async fn fetch_funding_rate(&self, symbol: &str) -> Result<FundingRate>;
}
```

#### 2.2.2 套利计算模块 (`arbitrage/`)

**职责**:
- 计算价差、清仓价差、净资金费率
- 检测套利机会

**关键组件**:
- `ArbitrageCalculator`: 套利计算器
  - `calculate_spread()`: 计算价差 `[2 × (Price_A - Price_B)] / (Price_A + Price_B) × 100%`
  - `calculate_close_spread()`: 计算清仓价差
  - `calculate_net_funding_rate()`: 计算净资金费率
- `ArbitrageDetector`: 套利机会检测器
  - `detect_spot_futures_arbitrage()`: 检测期现套利
  - `detect_futures_futures_arbitrage()`: 检测期期套利

**算法**:
- 价差公式: `[2 × (Price_A - Price_B)] / (Price_A + Price_B) × 100%`
- 清仓价差: 与开仓价差符号相反
- 净资金费率: 考虑做多和做空方向

#### 2.2.3 监控模块 (`monitor/`)

**职责**:
- 实时监控价格波动
- 推送通知（Telegram）

**关键组件**:
- `VolatilityMonitor`: 价格波动监控器
  - `monitor_spread()`: 监控价差
  - `monitor_basis_volatility()`: 监控基差波动（1/5/60分钟）
  - `monitor_funding_rate_volatility()`: 监控资金费率波动（1/5/60分钟）
- `NotificationService`: 通知服务
  - 支持 Telegram 推送
  - 可扩展其他通知渠道

**数据结构**:
- 使用 `DashMap` 存储历史数据用于波动计算
- 定期清理旧数据（保留2小时）

#### 2.2.4 存储层 (`storage/`)

**设计模式**: Repository Pattern

**职责**:
- 数据库连接管理
- 数据持久化
- 查询接口

**关键组件**:
- `Database`: 数据库连接池管理
  - 使用 `deadpool-postgres` 实现连接池
  - 自动初始化表结构
- `Repository`: 数据访问层
  - `save_price_data()`: 保存价格数据
  - `save_funding_rate()`: 保存资金费率
  - `save_arbitrage_opportunity()`: 保存套利机会
  - `save_volatility_event()`: 保存波动事件

**数据库设计**:
- `trading_pairs`: 交易对信息
- `price_data`: 价格时序数据（考虑分区或 TimescaleDB）
- `funding_rates`: 资金费率数据
- `arbitrage_opportunities`: 套利机会
- `volatility_events`: 价格波动事件

**性能优化**:
- 连接池管理（默认20个连接）
- 索引优化（时间戳、交易所、交易对）
- 考虑时序数据库（TimescaleDB）用于价格数据

#### 2.2.5 API 服务层 (`api/`)

**职责**:
- 提供 REST API 查询接口
- 支持外部系统集成

**计划中的端点**:
- `GET /api/v1/arbitrage/opportunities` - 查询套利机会
- `GET /api/v1/arbitrage/opportunities/{id}` - 查询特定套利机会
- `GET /api/v1/prices/{exchange}/{symbol}` - 查询价格数据
- `GET /api/v1/funding-rates/{exchange}/{symbol}` - 查询资金费率
- `GET /api/v1/volatility-events` - 查询波动事件

**技术选型**:
- 计划使用 `axum` 或 `warp` 框架
- 异步处理，支持高并发

#### 2.2.6 配置管理 (`config/`)

**职责**:
- 统一管理配置
- 支持环境变量和配置文件

**配置项**:
- 数据库连接
- 交易所配置
- 数据收集频率
- 监控阈值
- 通知配置
- API 端口

**优先级**:
1. 环境变量
2. 配置文件
3. 默认值

## 3. 数据流

### 3.1 数据收集流程

系统采用**任务分离架构**，将低频和实时任务分开，确保性能优化：

**任务1: 交易对收集（独立运行，1小时一次）**
```
定时任务触发（1小时）
    ↓
同步交易对列表（所有交易所）
    ↓
保存到数据库
    ↓
更新监控列表
```

**任务2: 实时数据收集（独立运行，高频）**
```
定时任务触发（5秒/5分钟）
    ↓
批量获取价格数据
    ↓
检测套利机会
    ↓
保存到数据库
    ↓
推送通知 (如果满足条件)
```

**设计优势：**
- 任务隔离：低频耗时任务不影响实时任务
- 性能优化：价格同步保持稳定的5秒间隔
- 故障隔离：交易对收集失败不影响实时监控

### 3.2 价格监控流程

```
获取价格数据
    ↓
计算价差/基差/资金费率
    ↓
与历史数据比较
    ↓
判断是否超过阈值
    ↓
生成波动事件
    ↓
保存到数据库
    ↓
推送 Telegram 通知
```

### 3.3 API 查询流程

```
HTTP 请求
    ↓
API Handler
    ↓
Repository 查询
    ↓
数据库查询
    ↓
数据转换
    ↓
JSON 响应
```

## 4. 并发模型

### 4.1 异步并发

使用 Tokio 异步运行时实现高并发：

- **任务分离**: 
  - 交易对收集任务（独立运行，1小时一次，低频耗时）
  - 实时数据收集任务（独立运行，高频实时）
- **价格同步**: 并发请求多个交易所（5秒间隔）
- **资金费率同步**: 并发同步资金费率（5分钟间隔）
- **套利检测**: 并发检测多个交易对
- **独立任务**: 每个任务在独立的 `tokio::spawn` 中运行，真正并行执行

### 4.2 线程安全

- `Arc<Mutex<T>>` 或 `Arc<RwLock<T>>` 用于共享状态
- `DashMap` 用于并发 HashMap
- `deadpool-postgres` 提供线程安全的连接池

## 5. 错误处理

### 5.1 错误类型

使用 `anyhow` 和 `thiserror` 进行错误处理：

- **网络错误**: 交易所 API 调用失败
- **数据解析错误**: JSON 解析失败
- **数据库错误**: 数据库操作失败
- **配置错误**: 配置加载失败

### 5.2 错误恢复

- **重试机制**: 网络请求失败时自动重试
- **降级策略**: 部分交易所失败时继续运行其他交易所
- **日志记录**: 所有错误记录到日志

## 6. 性能优化

### 6.1 任务分离架构

**核心优化：任务分离**
- **低频任务独立运行**: 交易对收集（1小时一次）在独立任务中运行，不影响实时任务
- **实时任务优先**: 价格同步和资金费率同步在独立任务中运行，确保及时性
- **避免任务阻塞**: 通过任务分离，确保高频任务不会被低频耗时任务阻塞

**性能提升：**
- 价格同步延迟从可能延迟5-30秒降低到稳定的5秒间隔
- CPU使用更均匀，避免任务间的相互影响
- 更好的资源隔离和故障隔离

**架构对比：**
```
优化前: 单任务循环 (可能阻塞)
├─ 交易对收集（1小时） ← 阻塞其他任务
├─ 价格同步（5秒）
└─ 资金费率（5分钟）

优化后: 任务分离（独立运行）
任务1: 交易对收集（独立运行）
├─ 1小时执行一次
└─ 不影响其他任务

任务2: 实时数据收集（独立运行）
├─ 价格同步（5秒）
└─ 资金费率（5分钟）
```

### 6.2 数据获取

- **批量请求**: 尽可能批量获取价格数据
- **连接复用**: HTTP 客户端连接池
- **超时控制**: 避免长时间等待
- **任务隔离**: 低频和实时任务分离，确保实时性

### 6.3 数据库

- **连接池**: 复用数据库连接
- **索引优化**: 在查询字段上建立索引
- **批量插入**: 使用批量插入提高性能
- **数据分区**: 时序数据考虑分区

### 6.4 内存管理

- **数据缓存**: 使用内存缓存常用数据
- **定期清理**: 定期清理历史数据
- **零拷贝**: 尽可能使用引用而非克隆

## 7. 扩展性设计

### 7.1 添加新交易所

1. 在 `exchange/` 目录下创建新的适配器文件
2. 实现 `ExchangeAdapter` trait
3. 在 `exchange/mod.rs` 中导出
4. 在配置文件中添加新交易所配置
5. 在 `main.rs` 中注册适配器

### 7.2 添加 DEX 支持

- 创建 `exchange/dex/` 模块
- 实现 DEX 适配器（可能需要 Web3 集成）
- 复用现有的套利检测逻辑

### 7.3 添加新的套利类型

- 在 `ArbitrageType` 枚举中添加新类型
- 在 `ArbitrageDetector` 中添加检测方法
- 更新数据库 schema
